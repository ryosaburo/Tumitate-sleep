# ねかせ — 開発の進め方(GitHub 入門編)

GitHub からファイルを自分のパソコンに持ってきて、変更して、Pull Request(PR)を出すまでの手順です。
Git や GitHub が初めてでも、上から順にやれば進められます。

> **この手順の約束はひとつだけ:`main` に直接変更を入れない。** 必ず「自分のブランチ」で作業して、PR にします。

---

## 用語(先に3分で)

| 言葉 | 意味 |
|---|---|
| リポジトリ | プロジェクトのファイルと、変更の履歴をまとめた入れ物 |
| クローン(clone) | GitHub 上のリポジトリを、自分のパソコンにコピーすること。**最初に1回だけ** |
| ブランチ | 変更を試すための「作業用のコピー」。`main` は完成品の線で、自分の作業は別の線で行う |
| コミット(commit) | 変更を「ここまで」と区切って、メモ(メッセージ)つきで記録すること |
| プッシュ(push) | 自分のパソコンのコミットを、GitHub に送ること |
| Pull Request(PR) | 「この変更を `main` に入れてください」というお願い。仲間が見て(レビューして)、OK なら取り込む |
| マージ(merge) | PR の変更を、`main` に取り込むこと |

流れ全体はこうです。

```
クローン(最初の1回) → 最新にする → ブランチを作る → 作業する → 確認する
   → コミット → プッシュ → PR を作る → レビュー → マージ → 最新にして、次の作業へ
```

---

## 0. 最初の準備(1回だけ)

必要なもの: Git、Node.js 22 以上、VS Code、GitHub のアカウント(リポジトリへの招待を承認しておく)。

ターミナルは、VS Code の画面上のメニュー「ターミナル → 新しいターミナル」で開けます。

```
git --version        # バージョンが出れば OK
node --version       # v22 以上であれば OK
```

初めての Git では、名前とメールを設定します(コミットに記録されます)。

```
git config --global user.name "あなたの名前"
git config --global user.email "GitHub に登録したメールアドレス"
```

### クローン(コピーを持ってくる)

```
git clone https://github.com/ryosaburo/Tumitate-sleep.git nekase-kit
cd nekase-kit
```

VS Code で、そのフォルダを開きます(「ファイル → フォルダーを開く」)。

### 道具を入れる

```
corepack enable
pnpm install
```

- Mac: `nvm use` で、Node のバージョンが自動で合います。
- Windows(nvm-windows の場合): `.nvmrc` は読まれないので、`nvm use 22` と打ちます。

`pnpm check` を実行して、エラーなく終われば、準備は完了です。

> うまくいかないときは、**エラーの全文**をそのまま AI に貼って、「原因と直し方を平易に説明して」と頼みます。

## 1. 作業のたびに、やること(毎回の流れ)

### 手順1: 最新の状態にする

作業を始める前に、`main` を最新にします。

```
git switch main
git pull
```

> `main` では、**ファイルを変更しません**。見るだけです。

### 手順2: 自分のブランチを作る

1つの作業(1つの目的)につき、1つのブランチを作ります。

```
git switch -c feat/ブランチ名
```

名前の付け方(英語・小文字・ハイフン区切り):

| 種類 | 例 |
|---|---|
| 機能を追加 | `feat/sleep-screen` |
| 不具合の修正 | `fix/wake-time-bug` |
| 文書の変更 | `docs/update-readme` |

今どのブランチにいるかは、`git branch` で確認できます(`*` が付いているのが今のブランチ)。

### 手順3: 作業する(AI と一緒に)

使う AI は、自分が使えるものでかまいません(チャット型でも、VS Code に入れる型でも)。

1. 使う AI を開く。
2. 最初に、`CLAUDE.md` と `docs/nekase-plan.md` の内容を、AI に読ませる(ファイルを読める AI なら読ませる。読めない AI には、中身を貼る)。このプロジェクトの決まりごとを、AI に先に伝えるためです。
3. `docs/claude-code-prompts.md` の、自分の担当のステップの依頼文を貼る(ファイル名に Claude とありますが、ほかの AI でも使えます)。
4. AI が「やることの説明」を出したら、読んで、**わからなければ質問してから**進める。
5. AI が出したコードは、そのままファイルに反映する前に、何をするコードかを説明してもらう。
6. 一度にたくさん頼まない。**1つの作業は、1つの目的**にする。

> 迷ったときの合言葉: 「変更する前に、やることを3行で説明して。私が OK と言ってから実装して」

### 手順4: 確認する

PR を出す前に、必ずこれを実行します。

```
pnpm check
```

型チェック・コードの書き方のチェック・テストを、まとめて実行します。**エラーが出たら、直してから進みます。** 画面の変更なら、実際に動かして見た目も確認します(`pnpm -F mobile web`)。

### 手順5: コミット(変更を記録する)

まず、何を変更したかを確認します。

```
git status        # 変更したファイルの一覧
git diff          # 変更の中身
```

見覚えのないファイルや、パスワード・キー(`.env`、`.dev.vars` など)が入っていないかを、**必ず**見ます。

問題なければ、記録します。

```
git add ファイル名       # コミットに入れるファイルを選ぶ(複数なら、スペースで区切る)
git commit -m "メッセージ"
```

メッセージは、**日本語で、何をしたかが1行でわかる**ようにします。

- 良い例: `設定画面に、目標時刻の入力欄を追加`
- 悪い例: `修正`、`いろいろ変更`

コミットは、**小さく、こまめに**します(大きな1つより、小さな5つのほうが、レビューしやすい)。

> AI に「コミットして」と頼めるツールを使っているなら、頼んでもよいです。そのときも、手順5の `git status` と `git diff` で、何が入るかを自分の目で確認します。

### 手順6: プッシュ(GitHub に送る)

初めて送るときは、このように打ちます。

```
git push -u origin feat/ブランチ名
```

2回目以降は、`git push` だけで済みます。

### 手順7: PR を作る

1. ブラウザで、リポジトリのページ(https://github.com/ryosaburo/Tumitate-sleep)を開く。
2. 黄色い帯の「**Compare & pull request**」ボタンを押す。出ていなければ、「Pull requests」タブ →「New pull request」→ 自分のブランチを選ぶ。
3. 次の形で、タイトルと説明を書く。
   - **base**(取り込み先)が `main` になっていることを確認する。
4. 「**Create pull request**」を押す。

**タイトル**: 何をしたかが1行でわかるように(日本語でよい)。

**説明のひな形**(コピーして使う):

```
## 目的
(この PR で何をするか。1〜2行)

## 変更
- (変更した内容を、箇条書きで)

## 確認したこと
- [ ] `pnpm check` が通った
- [ ] (画面の変更なら)実際に動かして確認した

## レビューしてほしい点
(迷ったところ、見てほしいところ。なければ「なし」)
```

### 手順8: レビューと、マージ

- チームのメンバーが、PR を見て、コメントや「承認」をくれます。
- 直してほしい点があったら、**同じブランチで直して、コミットして、`git push`** します。PR は自動で更新されます(PR を作り直す必要はありません)。
- 承認されたら、「Merge pull request」を押して、マージします(誰が押すかは、チームで決めておく)。

### 手順9: マージのあとの片づけ

```
git switch main
git pull
```

次の作業は、**手順2から**繰り返します(新しいブランチを作る)。使い終わったブランチは、そのまま放置してかまいません(消したいときは、`git branch -d ブランチ名`)。

## 2. 困ったときの早見表

| 状況 | 対処 |
|---|---|
| 今どのブランチにいるか、わからない | `git branch`(`*` が付いているのが今のブランチ) |
| `main` にいるのに、ファイルを変更してしまった | コミットする**前**なら、`git switch -c feat/ブランチ名` で新しいブランチを作る。変更はそのままついてくる |
| `main` でコミットしてしまった | **プッシュしないで**、チームの誰かに相談する |
| `git push` が拒否された(rejected) | エラーの全文を、AI に貼って相談する。`--force` は、**自分では打たない** |
| `git pull` で「競合(conflict)」と出た | 慌てず、**何も消さずに**、チームの誰かに相談する |
| 間違えたファイルを `git add` した | `git restore --staged ファイル名` で、取り消せる |
| 何をしたか、わからなくなった | AI に「ここまでの変更を、ファイルごとに3行以内でまとめて」と頼む |
| 変更が大きくなりすぎた | AI に「いったん止めて。今の変更を、目的ごとに分けて提案して」と頼む |
| エラーが出た | エラーの**全文**を貼って、「原因と直し方を、平易に説明して。直す前に、方針を教えて」と頼む |

**どんなときも、「わからないまま進まない」。** 聞くことは、失敗ではありません。

---

## 3. やってはいけないこと

- **`main` に直接コミットしない。** 必ずブランチ → PR。
- **シークレットをコミットしない。** `.env`、`.dev.vars`、トークン、API キー、AWS のアクセスキーなど。うっかり入れたら、プッシュする前なら、すぐに相談する。**プッシュしてしまったら、そのキーは使えないものとして、作り直す**(消すだけでは足りない)。
- **`git push --force` や `git reset --hard` を、自分の判断で打たない。** 変更が消えることがある。
- **仲間のブランチを、勝手に変更しない。**
- **仕様にない機能を、足さない。** 迷ったら、聞く。仕様の正は `docs/nekase-plan.md`。
- **AWS の `cdk deploy` などの、お金がかかる・消えるコマンドは、チームの OK なしに実行しない。**

## 4. 1枚にまとめた手順(印刷用)

```
【最初の1回】 git clone → cd nekase-kit → corepack enable → pnpm install

【毎回】
 1. git switch main && git pull          最新にする
 2. git switch -c feat/ブランチ名         自分のブランチを作る
 3. (AI と作業)                           1つの目的だけ
 4. pnpm check                            エラーなしを確認
 5. git status / git diff                 変更の中身を、自分の目で見る
    git add ファイル名 → git commit -m "日本語のメッセージ"
 6. git push -u origin feat/ブランチ名     GitHub に送る
 7. GitHub で「Compare & pull request」→ 説明を書いて作成
 8. レビュー → 直しがあれば、コミットして git push → 承認 → マージ
 9. git switch main && git pull          次の作業へ(手順2から)
```
