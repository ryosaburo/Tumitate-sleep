> 眠る習慣が、仮想の資産を育てる。
> 睡眠改善が主役、投資の学び(積立・FX 的な判断の練習)は、睡眠を守る仕組みの中で体験する。

- 状態: **ドラフト v1.2**(FX の「AI による注文の代行」を追加。AWS の学習モジュールは v1.1。「未決事項」は暫定の既定値で進め、確定したら更新する)
- 位置づけ: ハッカソン(2週間)で、動くデモと公開 URL を作るための計画書

## 1. 目的とターゲット

**解決したい課題**: 睡眠不足の解消と、睡眠の質の向上。

**ターゲット**: 投資に慣れていない、睡眠に悩む人。

**投資要素の位置づけ**: 副産物。実際の売買・換金は一切なく、すべて仮想(学習用シミュレーション)。

**ゴール(ハッカソン)**
- 誰でも(機器なしで)睡眠を記録でき、PC とスマホで記録を引き継げる。
- 睡眠の行動が、仮想の積立資産の成長として見える。
- 睡眠と投資の判断の関係を、FX 的な体験で学べる(睡眠を守る安全装置つき)。
- (任意)就寝時刻が乱れた日に、AI に注文を代行してもらい、判断がぶれる様子を体験できる(§6.6)。
- Cloudflare 上に公開された URL で、審査員が触れる。
- (学習目的)AWS で、匿名の利用状況を集めて週ごとにまとめる小さな仕組みを、コードで作って運用する(§8.6)。

**やらないこと**: 実取引、換金できる報酬、ストア公開、医療行為・診断、個別銘柄の推奨。

## 3. 決定事項

| # | 決定 | 理由 |
|---|---|---|
| D1 | 睡眠は「ねる」「おきた」ボタンで記録する。「ねる」は押してそのまま眠る | 機器なしで誰でも使える。見たいのは時刻の規則性なので、センサーは不要 |
| D2 | 報酬は睡眠の「結果」ではなく「行動」に付ける | 結果に付けると、眠れない人ほど焦りが増える |
| D3 | 目標時刻の前後30分を達成とする。週5日できれば OK | 1日の失敗で崩れない。ポケモンスリープの「ねむりの約束」に近い設計 |
| D4 | 積立は自動。仮想ファンドは世界株式・債券・現金の3つ | 簡単さを最優先 |
| D5 | 評価額を、積立元本・運用益・複利の分に色分けして見せる | 複利を目で見えるようにする |
| D6 | 同期は匿名アカウント+引き継ぎコード方式 | ログイン画面なしで、PC とスマホを同じ記録でつなげる |
| D7 | 記録は端末内保存が基本。サーバーには日付・時刻・チェックだけを同期する | プライバシーと開発の軽さ |
| D8 | FX 的な要素は「任意のチャレンジ」。資金は別枠で、積立資産に影響しない | 罰を与えない方針を保つ |
| D9 | FX は睡眠に連動する安全装置(判断力ゲージ、夜間ロック、確認ステップ)とセットで入れる | FX だけ入れると、睡眠改善という目的とぶつかる |
| D10 | 値動きは仮想データ。実在の相場データは使わない(MVP) | 利用条件の確認が不要。下落局面を作れる |
| D11 | 「ねる」を押したあとは、暗い「おやすみ画面」にする。資産・FX・通知は出さない | 寝る前に相場や損益を見る状況を避ける |
| D12 | AWS は構成の学習のために使う。記録・同期・引き継ぎ・FX の本体は Cloudflare(D1)のままにする | データの置き場所を2つにすると、どちらが正か曖昧になる。AWS が止まっても本体は動く |
| D13 | AWS には「運営用の匿名イベントの集計」だけを持たせる(候補Aに決定) | 本体と役割が重ならず、睡眠の記録を送らずに済む |
| D14 | AWS に送るのは、イベントの種類・サーバー時刻・プラットフォーム・アプリの版だけ。アカウント ID、睡眠の時刻、取引の内容は送らない | プライバシーを守る。送る範囲を、最初に固定する |
| D15 | FX の注文は、ユーザーが「AI にまかせる」と選んだときに限り、AI が代行できる(任意)。代行した注文は、ユーザーのチャレンジ資金で成立し、損益もそこに反映する | 就寝の乱れが判断のぶれにつながる様子を、自分の資金で体験させるため。毎日自動で動かさず、ユーザーが選んだときだけにする |
| D16 | AI の判断の質は、判断力ゲージで変える。ゲージが低い日は衝動的、高い日は規則に沿う、という「学習用の設定」にする。実際の睡眠不足が判断を悪くすると断定しない | 結果ではなく行動の規則性で動かす方針(D2)を守る。因果の断定を避ける |
| D17 | AI は Cloudflare Workers AI を、サーバー側(Workers)からだけ呼ぶ。AI に渡すのは、仮想レートの直近の動き・ゲージの数値・注文の上限だけ。返答は、形を固定して検証し、core の注文検証(損切り必須・上限・1日1回・夜間ロック)を必ず通す | データの置き場所を Cloudflare に保つ(D12)。AI の誤りや不正な返答で、安全装置が外れないようにする |

## 5. 機能仕様(睡眠・積立)

### 5.1 睡眠の記録

- **ねる**: 押した時刻を「就寝」として一時保存する。そのあと、おやすみ画面に切り替える。
- **おきた**: 押した時刻を「起床」として、「ねる」とセットで、起床日の記録として保存する。
- **取り消し**: 「ねる」を押したあとに、取り消せる。
- **古い記録の扱い**: 「ねる」から18時間以上たっていたら破棄し、時刻の入力を促す。
- **修正**: 日付を選び、就寝・起床の時刻を入力できる。起床は就寝より後で、16時間以内であること。
- **時刻の軸**: 20:00 を起点の0分とする(20:00〜23:59 は 0〜239、0:00 以降は +1440)。表示範囲は 20:00〜12:00(960分)。
- 睡眠時間は「推定値」と明記する。

### 5.2 行動課題

| キー | 課題 | 判定 |
|---|---|---|
| `bed` | 就寝時刻を守る | 自動(目標の前後30分以内) |
| `wake` | 起床時刻をそろえる | 自動(目標の前後30分以内) |
| `screen` | 寝る1時間前に画面を閉じる(このアプリの画面は対象外) | 自己申告 |
| `caffeine` | 夕方以降はカフェインを控える | 自己申告 |

- 2〜3個を選ぶ(最小2、最大3)。
- 目標時刻の初期値は就寝 23:30 / 起床 06:30。設定で変えられる。

### 5.3 積立

- **達成率** = 達成した課題数 ÷ 選んだ課題数
- **積立額** = 基準額 ¥3,000 × 達成率(100円単位で丸める)
- **クリア日** = 選んだ課題の過半数を達成した日
- **週5日クリア**で、その週は「達成」
- 課題をできなかった日は、積立が止まるだけ。資産は減らさない。積立済みの分は、そのまま育つ。

**配分プリセット(世界株式 / 債券 / 現金)**

| 名前 | 世界株式 | 債券 | 現金 |
|---|---|---|---|
| 守り重視 | 20% | 50% | 30% |
| バランス(既定) | 60% | 30% | 10% |
| 成長重視 | 80% | 15% | 5% |

### 5.4 仮想の値動き

- 30日分の日次リターンのシナリオを、`packages/core` に定数として持つ(プロトタイプの `R_EQ` / `R_BD`)。
- 世界株式は、8〜18日目に最大 −14.4% の下落を含む。債券は小さな変動。現金は 0%。
- 自分の記録モードでも、開始日から30日で1周とする。31日目以降は、設定でリセットして新しく始める。

### 5.5 評価額の内訳(複利の分)

毎日、運用前の評価額を `base = 前日の評価額 + 当日の積立額` とし、`gain = 当日の運用後の評価額 − base` とする。

```
A += gain × 積立元本累計 / base          // 積立元本が生んだ分
B += gain × 前日までの損益 / base        // それまでの損益が生んだ分(= 複利の分)

損益 G = 評価額 − 積立元本累計
G > 0 のとき:  複利の分 = clamp(B, 0, G)   運用益(元本分) = G − 複利の分
G < 0 のとき:  元本割れ = −G
```

- 30日では、複利の分はごく小さい(約 ¥79 前後)。表示で隠さず、「期間が短いため、まだ小さな値」と案内する。
- 将来の拡張: 睡眠を守った日数に応じて、仮想の期間を延ばす(複利が見える長期モード)。

### 5.6 答え合わせ(30日目)

- 就寝のズレ: 初週と直近7日の比較。
- 資産: 積立元本 → 評価額、複利の分。
- 値下がりの最中も続けた結果: 積立した時期(下落の前・最中・回復のあと)ごとの増減。
- 「結果を知ってから分かることで、同じ展開になる保証はない」「仮想データ」と明記する。

### 5.7 週ごとの振り返り

- 週ごとのクリア日数(7個のドット)、就寝のズレの平均、週末の評価額。
- 就寝のズレは、3日分以上の記録がある場合のみ表示する。

## 6. 機能仕様(FX 的な要素: チャレンジ)

> 位置づけ: 睡眠を守る安全装置つきの、任意の「判断の練習ゲーム」。実際の FX 取引ではない。

### 6.1 積立との役割分担

| | 積立 | FX 的な体験(チャレンジ) |
|---|---|---|
| 狙い | 習慣の継続と複利を体感する | 判断と感情のコントロールを練習する |
| 操作 | 自動 | 1日1回、自分で判断する |
| 資金 | 睡眠の行動で毎日増える | 別枠。週5日クリアすると、翌週の分が付与される |
| 損益の影響 | — | 積立資産には影響しない |
| 使える時間 | いつでも | 日中のみ(夜間ロックあり) |

### 6.2 取引のルール(暫定)

| 項目 | 内容 |
|---|---|
| 通貨ペア | 最初は USD/JPY の1つ。余裕があれば EUR/JPY、AUD/JPY を追加 |
| レート | 仮想の日足の終値(シナリオ。初期値は 150.00 付近の架空の値) |
| 注文 | 「円安になる(買い)」か「円高になる(売り)」を選ぶ |
| 注文額 | ¥1,000 刻み。チャレンジ資金の20%まで(レバレッジなし)。確認ステップが出る日は、その半分まで |
| 損切り | **必須**。約定レートから 0.5% / 1% / 2% の3択 |
| 約定 | 注文した日の仮想レート |
| 決済 | 翌日の終値。ただし、翌日の終値が損切りラインを超えていたら、損切りラインのレートで決済する |
| 回数 | **1日1回まで** |
| 初期資金 | ¥10,000 |
| 付与 | 週5日クリアで、翌週に ¥10,000(上限 ¥50,000) |
| 資金が0 | 付与を待つ(「次の達成で、また始められます」と案内する) |

**損益** = 注文額 × (決済レート ÷ 約定レート − 1) × (買い: +1 / 売り: −1)

### 6.3 睡眠との連動

**判断力ゲージ(0〜100)**

```
MAD7  = 直近7日の就寝時刻の、目標からのズレの平均(分)。記録のある日が3日以上のとき
gauge = round(100 × clamp(1 − MAD7 / 90, 0, 1) × span)
記録が3日未満のとき: 50(中)
span  = 目標の就寝〜起床の間隔による係数。6時間以上は 1、6時間未満は直線で下げ、4時間以下で 0.6
```

- `span` は設定した**目標**だけを見る(実際の睡眠時間は使わない)。目標を短く設定すると、規則的でもゲージが上がりにくい。設定画面で、目標が6時間未満のときに説明を出す。

| レベル | ゲージ | 動き |
|---|---|---|
| 高 | 70以上 | 通常どおり |
| 中 | 40〜69 | 通常どおり。目安を表示 |
| 低 | 40未満 | **確認ステップ**を挟む。注文額の上限を半分にする |

- 結果(睡眠時間やスコア)は使わず、**行動の規則性**だけで計算する。
- 「睡眠が乱れると判断が荒れる」と断定しない。表示は「傾向」「目安」にする。

**確認ステップ(ゲージが低い日)**
1. 理由を選ぶ(なんとなく / 取り返したい / ニュースを見た / 予想に自信がある / 練習)。
2. 10秒のカウントダウン。
3. 「それでも注文する」を選んだ場合のみ、確定する。

**夜間ロック**
- 目標就寝の2時間前〜目標起床の1時間後は、チャレンジ画面を開けない。
- ロック中は、「おやすみの時間です」と表示する。

### 6.4 取引ログと振り返り

- 取引ごとに、日付、通貨ペア、売買、注文額、約定レート、損切り、決済レート、決済の理由(終値 / 損切り)、損益、そのときのゲージ、選んだ理由を記録する。
- 週に1度、ゲージ別(高・中・低)の取引数、勝った割合、平均損益を表示する。
- **取引が10件に満たないうちは、「参考値」と表示する。** 因果関係は断定しない。
- 二段グラフに、取引した日のマーカー(買い ▲ / 売り ▼)を重ねる。

### 6.5 安全装置(やらないこと)

- 現金や換金できる報酬、賞品つきのランキングを付けない。
- レート変動の通知を出さない。
- 損失を強調する演出(赤の点滅など)を入れない。
- 3回連続で損失になったら、「今日は休む」を提案する(強制はしない)。
- 実在の FX 会社への誘導を入れない。
- 画面に「学習用シミュレーション」「投資助言ではありません」と明記する。

### 6.6 AI による注文の代行(任意)

> 位置づけ: 就寝時刻が乱れた日の「判断のぶれ」を、AI に注文させることで体験する、学習用の仕組み。**実際の睡眠不足が判断を悪くすると示すものではない**(D16)。

**目的**: 判断力ゲージが低い日の AI は、衝動的な注文をする。その結果と理由を見て、「就寝の規則性」と「判断」の関係を考えるきっかけにする。

**基本のルール**

| 項目 | 内容 |
|---|---|
| 使い方 | チャレンジ画面で「AI にまかせる」を選ぶと、AI がその日の注文(買い・売り・見送り、注文額、損切り)を決めて、確定する。選ばなければ、今までどおり自分で注文する |
| 回数 | 注文は**1日1回**(自分の注文と AI の注文を合わせて)。AI が「見送り」を選んだ日は、注文なしで1日を終える(同日に、自分で注文し直すことはできない) |
| 資金 | ユーザーのチャレンジ資金。損益もそこに反映する。積立資産には影響しない(D8) |
| 安全装置 | 夜間ロック、損切り必須(0.5 / 1 / 2%)、注文額は資金の20%まで(ゲージが低い日は半分)、3連敗で「今日は休む」の提案を、**AI の注文にも同じく適用する**。AI の返答は、core の注文検証を通ったものだけを採用し、通らなければ注文しない |
| 確認ステップ | ゲージが低い日は、「AI にまかせる」の前に、理由の選択 → 10秒 → 再確認を挟む(§6.3 と同じ) |
| 確定前の説明 | 「AI にまかせる」を押す前に、「AI は今日のゲージ(目安)に合わせた設定で判断します。結果は保証されません」と表示する |

**ゲージによる AI の設定(学習用の演出)**

| ゲージ | AI の設定(指示の方針) |
|---|---|
| 高(70以上) | 直近の値動きと損切り幅を比べて、規則に沿って判断する。迷ったら見送る |
| 中(40〜69) | 規則に沿うが、直近の値動きにやや引っ張られる |
| 低(40未満) | 直近の値動きに飛びつく(上がったあとに買い、下がったあとに売る)。損切りは理由なく狭く(0.5%)、または広く(2%)選びがち。見送りを選びにくい |

- 設定の文面は、`packages/core` に定数として置き、テストで固定する(画面にも、同じ説明を出す)。
- AI は、注文と一緒に、短い理由(日本語、80字程度)を返す。理由は取引ログに残し、画面に表示する。
- 「高い・低いが損益を決める」とは表現しない。結果は、運や相場にも左右される。取引が10件未満の成績は、これまでどおり「参考値」。

**呼び出しの流れ**

```
端末(チャレンジ画面)
  └─ POST /v1/fx/ai-order { 直近のレート(最大7本)、ゲージ、注文額の上限、損切りの選択肢 }
       └─ Workers(Hono + Zod)── Workers AI(env.AI)
            ← { side: buy | sell | skip, amount, stopPct, comment }
       └─ Zod で検証 → 範囲に収める(上限・刻み・損切りの3択)
  ← 端末は、core の validateOrder を通して、注文として保存する
```

- AI に**送らない**もの: アカウント ID、睡眠の時刻、記録の中身、メール・名前。送るのは、仮想レートとゲージの数値、注文額の上限だけ(D17)。
- 認証つきで、アカウントあたり1日の回数を制限する(試行の乱用と、無料枠の使い切りを防ぐ)。
- AI が失敗・遅延(10秒で打ち切り)・不正な返答のときは、**注文せず**、「AI が使えませんでした。自分で注文できます」と案内する(勝手に別のルールで注文しない)。
- 取引には、「だれが注文したか」(`placed_by`: `user` / `ai`)と AI の理由を記録する。取引ログと、ゲージ別の成績に「AI 代行」を区別して表示する。
- AI の返答は毎回変わりうる。デモ用に、結果を固定したい場合は、記録済みの取引を見せる(予備の画面収録も用意する)。

**費用の方針**(できるだけ、かけない)

- Workers の**無料プランのまま**使う。Workers AI の無料枠は 1 日 10,000 ニューロン。無料プランでは、超えた分は課金ではなく**エラー**になる(有料プランに上げない限り、請求は発生しない)。エラーのときは、上の失敗時の動き(注文せず手動へ案内)になる。
- モデル: 既定は `@cf/meta/llama-3.3-70b-instruct-fp8-fast`(2026-10-17 に変更)。当初の `@cf/meta/llama-3.1-8b-instruct` は 2026-05-30 に廃止されて、AI 代行が動かなかった。代わりに試した `llama-3.1-8b-instruct-fp8` は JSON スキーマ非対応、`qwen3-30b-a3b-fp8` と `gemma-4-26b-a4b-it` は返答を読み取れず、動いたのは llama-3.3-70b だけだった(手元で、実際の Workers AI を呼んで確認)。モデルは、環境変数 `AI_MODEL` で入れ替えられる。
- 見積もり: **実測ではなく、要確認。** 70B のモデルは、以前の 8B より 1 回あたりのニューロンが多いと見込まれる(おおよそ 30 ニューロン前後の見込み)。1 日 300 回だと、無料枠(10,000)の上限に近い。ダッシュボードで実測して、`AI_GLOBAL_DAILY_LIMIT` を見直す。無料プランでは、超えた分は課金ではなくエラーになる。
- 安全装置: ①全アカウント合わせて 1 日 300 回まで(`AI_GLOBAL_DAILY_LIMIT`。無料枠に収まるかは、実測で確認する)、②アカウントあたり 1 日 3 回、③環境変数 `AI_DISABLED=1` で、AI を呼ばずに止められる。呼び出しは、ユーザーが「AI にまかせる」を押したときだけ(自動・定期の呼び出しはしない)。
- モデルは、JSON モードに対応した一覧の中から選ぶ。小さいモデル(1B / 3B)は、一覧にないので使わない(JSON が崩れて、失敗が増える)。
- 実際の使用量は、Cloudflare のダッシュボード(Workers AI の利用状況)で確認し、見積もりを実測に直す。

**やらないこと**
- AI に、実在の通貨・銘柄の売買を判断させない。実際のレートも渡さない。
- 通知で AI の注文や結果を知らせない。
- AI の判断を「おすすめ」「予想」と表現しない。投資助言ではない。
- ユーザーが選ばないまま、毎日自動で注文しない。

### 8.3 データモデル(D1。端末内保存も同じ形)

```sql
accounts(id TEXT PRIMARY KEY, token_hash TEXT, created_at INTEGER)

records(account_id TEXT, date TEXT,            -- 'YYYY-MM-DD'(起床日)
        bed_min INTEGER, wake_min INTEGER,     -- 20:00 起点の分。未記録は NULL
        screen INTEGER, caffeine INTEGER,
        updated_at INTEGER,
        PRIMARY KEY (account_id, date))

settings(account_id TEXT PRIMARY KEY,
         target_bed TEXT, target_wake TEXT, start_date TEXT,
         tasks_json TEXT, preset TEXT,
         pending_bed_ts INTEGER,               -- 「ねる」を押した時刻(未押下は NULL)
         updated_at INTEGER)

link_codes(code_hash TEXT PRIMARY KEY, account_id TEXT,
           expires_at INTEGER, used_at INTEGER)

fx_trades(account_id TEXT, id TEXT, date TEXT, pair TEXT, side TEXT,
          notional INTEGER, entry_rate REAL, stop_rate REAL,
          exit_rate REAL, exit_reason TEXT, pnl INTEGER,
          gauge INTEGER, reason TEXT, settled_at INTEGER, updated_at INTEGER,
          PRIMARY KEY (account_id, id))

fx_ledger(account_id TEXT, id TEXT, date TEXT, kind TEXT,  -- 'grant' | 'pnl'
          amount INTEGER, updated_at INTEGER,
          PRIMARY KEY (account_id, id))
```

- FX の取引(`fx_trades`)には、「だれが注文したか」(`placed_by`: `user` / `ai`)と、AI の理由(`ai_comment`)の列を足す。いまは端末内の保存(`fx_orders`)にだけ持つ。D1 への同期を作るときに、マイグレーションの新しいファイルで足す(既存は書き換えない)。

### 8.4 API

| メソッド・パス | 内容 |
|---|---|
| `POST /v1/accounts` | アカウントを作る。`{accountId, token}` を返す |
| `POST /v1/sync` | 認証つき。`{since, changes}` を送り、`{serverTime, changes}` を受け取る |

### 8.5 同期の方針

- 端末内に保存し、アプリを開いたときと、記録・取引を追加したときに同期する。ネットワークがなくても記録できる。
- 競合したときは、**あとから更新した方を採用**(行ごと)。順序の判定にはサーバー時刻を使う。
- 同期する対象: records、settings(「ねる」の状態を含む)、fx_trades、fx_ledger。
- トークンは端末にだけ保存し、サーバーにはハッシュだけを置く。通信は HTTPS。
- 保存するデータは、日付・時刻・チェックの有無・取引の記録だけ。睡眠の音声やセンサーのデータは扱わない。

### 8.6 AWS の学習モジュール(運営用の匿名イベントの集計)

> 位置づけ: 構成の学習が目的の、任意の追加。本体(Cloudflare)とは独立していて、止まっても本体は動く。遅れたら、最初に切る(§4)。

**構成**

```
[アプリ / Web版] ──(匿名イベントを送る。失敗しても無視)──→ API Gateway(HTTP API)
                                                          │
                                                          ▼
                                                       Lambda(受け口)
                                                          │ 条件つき書き込み(同じイベントは1回だけ)
                                                          ▼
                                              DynamoDB: events(90日で自動削除)
                                                          ▲
EventBridge Scheduler(週1回、デモ用に手動実行も可)──→ Lambda(集計)──→ DynamoDB: weekly_summary
                                                          │
                                  GET /v1/summary(キー認証)←── 運営ダッシュボード(読み取り専用)
CloudWatch: ログ、エラー率のアラーム    Budgets: 予算の上限とアラート    すべて CDK でコード化
```

**送るイベント(D14 の範囲。これ以外は送らない)**

| `type` | 意味 |
|---|---|
| `sleep_start` / `sleep_end` | 「ねる」「おきた」を押した(時刻は送らない。サーバーが受けた時刻だけが残る) |
| `week_cleared` | その週が「達成」になった |
| `handover_done` | 引き継ぎが完了した |
| `fx_order_placed` | チャレンジで注文した(売買の向き・金額・損益は送らない) |
| `fx_confirm_shown` | 確認ステップが表示された |

- 項目は `eventId`(重複排除用の乱数)、`type`、`platform`(web / ios / android)、`appVersion` のみ。**アカウント ID、端末の識別子、睡眠の時刻、取引の内容は含めない。**
- 設定に「利用状況の送信」のオン・オフを置く。初回に、何を送るかを平易に説明する。
- 送信は、失敗しても画面に出さず、アプリの動作を止めない(再試行は少なく)。

**DynamoDB(最小)**
- `events`: PK `week`(サーバーが付ける `YYYY-Www`)、SK `ts#eventId`。TTL で90日後に削除。
- `weekly_summary`: PK `week`、SK `type#platform`、`count`。

**Lambda**
- 受け口: Zod で入力を検証し、許可した `type` のみ受け付ける。不明な項目は捨てる。`eventId` の条件つき書き込みで、重複を防ぐ。
- 集計: 対象の週の `events` を数え、`weekly_summary` に書く(何度実行しても同じ結果になる)。

**安全と運用**
- AWS アカウントのルートユーザーは使わない。権限を絞った IAM ユーザー(または IAM Identity Center)で作業する。アクセスキーをリポジトリや会話に貼らない。
- 最初に Budgets で予算の上限とアラートを設定する。リージョンは `ap-northeast-1`(東京)。
- API Gateway にレート制限をかける。CORS は、公開 URL のドメインだけに許可する。
- Lambda の権限は、必要な表への必要な操作だけにする(最小権限)。
- `GET /v1/summary` は、キーで保護する(キーは Systems Manager Parameter Store などに置き、コードに書かない)。
- イベント後は `cdk destroy` で片づける手順を、README に書く。

**学べること**: API Gateway、Lambda、DynamoDB(キー設計・TTL・条件つき書き込み)、EventBridge Scheduler、CloudWatch、Budgets、IAM(最小権限)、CDK によるコード化。

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| 無料の Apple ID では、アプリが7日で失効する。HealthKit が使えない可能性もある | 1日目に確認。HealthKit は任意にし、ボタン記録を主役にする。発表の直前に再ビルドする |
| iOS をビルドできるのが1人 | iOS が必要な作業(HealthKit のみ)を最小にし、他は Web で完結させる。実データの動作は、事前に画面収録しておく |
| 開発経験が浅い | 作業を小さく区切る。環境と雛形は A が用意する。AI の手伝いを前提にする |
| 同期のバグ | 競合ルールを単純にする(あとから更新した方)。同期は1つのエンドポイントに集約する |
| FX で範囲が膨らむ | 最小版(1通貨ペア、1日1回、損切り必須)に絞る。遅れたら §4 の順に切り捨てる |
| FX が睡眠改善と矛盾する | 夜間ロック、1日1回、通知なし、ゲージ連動の確認ステップ。FX は任意にする |
| 睡眠と成績の関係を断定してしまう | 「傾向」「目安」と表現する。取引が10件未満は「参考値」 |
| AI の代行が、「睡眠不足だと判断が悪くなる」という断定に見える | AI の設定は「学習用の演出」と明記する(§6.6)。画面にも説明を出し、因果は断定しない |
| AI が不正・極端な注文を返す | Zod で形を固定し、範囲に収め、core の注文検証を通す。通らなければ注文しない |
| AI の利用料金がかかってしまう | Workers 無料プランのまま使う(超過はエラーで、請求なし)。全体 1 日 300 回・アカウント 1 日 3 回の上限と、`AI_DISABLED` の緊急停止を置く(§6.6) |
| AI が遅い・失敗する・無料枠を使い切る | 10秒で打ち切り、注文せずに手動の注文へ案内する。1日の回数を制限する。デモは記録済みの取引と画面収録で補う |
| Web版と実機で、見た目や動作が違う | A が毎日、iPhone で確認する |
| AWS の学習で本体が遅れる | 日程を M2 のあとに置く。M3 が遅れたら、最初に切る(§4) |
| AWS の費用や権限の事故 | Budgets の上限とアラート、最小権限、ルートユーザー禁止、アクセスキーを貼らない、使い終えたら `cdk destroy` |
| AWS に個人のデータを送ってしまう | 送る項目を D14 で固定し、Zod で許可した項目だけを受ける。テストで確認する |
| 発表の当日に通信が不安定 | デモデータのモードは、オフラインでも動くようにしておく。予備の画面収録を用意する |

## 13. 免責・法務メモ(要確認)

- 画面に次を明記する: 「学習用のシミュレーションです。実際の売買や換金はできません」「睡眠の数値は目安で、医療上のアドバイスではありません」「眠れない日が2週間以上続くときは、医師に相談してください」。
- 実在の金融商品の売買、助言、誘導を行わない。外部のサービスへ送客しない。
- 実際のレートや相場データを使う場合は、提供元の利用条件を確認する。
- AI による注文の代行(§6.6)で Workers AI に送るのは、仮想レートの直近の動き、判断力ゲージの数値、注文額の上限だけ。睡眠の時刻、アカウント ID、記録の中身は送らない。Workers AI でのデータの扱い(学習への利用の有無など)は、Cloudflare の公式の説明で確認する。AI の設定は学習用の演出で、睡眠と判断の因果を示すものではなく、投資助言でもないことを、画面に明記する。
- AWS に送るのは、匿名のイベントの種類・サーバー時刻・プラットフォーム・アプリの版だけ(D14)。送る内容と、オフにする方法を、アプリと文書に明記する。
- 健康に関するデータの扱いは、プライバシーポリシーに明記する。公開する場合は、専門家に確認する。
- ポケモンスリープなど、既存のアプリを参考にする場合も、キャラクターやデザインは真似せず、独自のものを作る。
